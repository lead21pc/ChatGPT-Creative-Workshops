# Migration proposal from Router 3.2

Status: PROPOSAL ONLY. Router 3.2, CI v2.6, current lore, builder, package, and Project uploads are untouched. CI 3.0 is a readable proposal, not a verified installed control: PENDING CI 3.0 CONTRACT.

## Preserve, replace, defer

| Router 3.2 behavior | Router 4.0 disposition |
| --- | --- |
| PROMPT_ROUTE_ONLY before substantive execution | Preserve; module selection in this pass forms no premise or conclusion. |
| 00 then 92, current source, decisive 91, reconciliation, overlays, execution | Preserve the gate order; insert Module Gate after bootstrap and before source loading. |
| Source authority separate from read order; new source unconfirmed | Preserve; metadata and catalog never promote a source. |
| Old-canon quarantine; UNKNOWN and conflict remain open | Preserve without an archived-source fallback. |
| Missing decisive source blocked; narrow partial for nondecisive gaps | Preserve; add explicit node-to-full fallback first. |
| Full read of every routed file | Keep as default and safe fallback; replace the absolute rule only after approved VERIFIED_MODULE_CLOSURE is demonstrated in Project runtime. |
| Numeric CI discovery/selection in Router section 1 | Remove. CI 3.0 lives in Project instructions and calls Router; a repository file is not a runtime activation signal. |
| Fixed table from topic to 10/20/30/40/50/70/80 | Replace ordinary lore routes with admitted module headers plus 00's derived catalog. The existing table misses 60 even though 00 lists it. |
| Overlay selection and transitive dependencies | Preserve separately; activated overlays remain FULL_FILE. |
| 91 conflict/provenance evidence | Preserve FULL_FILE in phase one; RECORD_OR_FULL is a later, separate experiment. |

The 4.0 break is architectural, not a license to change canon: hardcoded ordinary lore routing becomes Module Gate -> candidate/admission -> module closure -> per-module mode -> node/full. Bootstrap routes for 00, 92, decisive 91, and overlays remain special because they are controls, not faction taxonomy.

## Staged migration and gates

1. Baseline: record repository commit and separately inspect the actual installed Project CI, Router, sources, overlays, and retrieval behavior. The repo copy does not prove installed bytes or Project file visibility.
2. Freeze a shadow source generation. Add headers to current-file copies without changing lore. Classify each file's effective admission and owner; leave 90/91/92 protected.
3. Generate a catalog section in a shadow 00 from those headers. Since build_consolidation.ps1 writes generated outputs directly, prove the catalog survives rebuilding from accepted inputs; do not manually patch only the generated root 00.
4. Compare old full-file routing to Router 4.0 with every module still FULL_FILE. Test discovery, cross-domain owners, open-state handling, reconciliation, overlay order, and new-module onboarding before any node optimization.
5. In a separate pilot, review a small module such as 80 for NODE_OR_FULL. Establish mandatory context, local index, target nodes, NODE_REQUIRES closure, exception coverage, and full fallback. Larger/mixed files remain full until independently reviewed.
6. Run Project-runtime shadow tests against the proposed CI 3.0/Router 4.0 pair and the same pinned source generation. A local parser or static test is not evidence that Project retrieval loaded the required content.
7. Only after explicit approval, release a mutually compatible CI instruction, Router, catalog, source generation, and overlays as one bounded activation. Preserve the previous full-file pair as rollback.

Do not migrate every 00-92 file in one operation, move old lore to fit a taxonomy, or rename files just to add a module. New faction, institution, region, actor, or subsystem sources can receive their own headers and catalog rows without a Router-core edit. A change to authority semantics, source-read contract, or Module Gate primitive does need versioned control review.

## Migration stop conditions

Stop before activation if the installed CI 3.0 contract differs from the candidate, the Project cannot reliably expose the catalog/header or prove node closure, the catalog fails to match the package, a controlling owner is ambiguous, a legacy mixed-status file would be promoted, or full-file and node-route paired tests disagree on decisive truth/authority. Keep v2.6/v3.2 as the default until a separate activation task explicitly changes it.
