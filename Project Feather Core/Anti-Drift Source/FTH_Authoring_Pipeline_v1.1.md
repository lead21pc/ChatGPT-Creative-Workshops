# FTH Authoring Pipeline v1.1

> Type: procedural authoring control, not an anti-drift overlay.
> Applies to: requested authoring transformations within Project Feather Core / FTH.
> Authority: subordinate to the active installed FTH CI. Controls transformation from input to seed, material primitives, comparison, or proposed implementation, and the requested stop point.
> Not: Router, canon or lore source, source authority, truth-status authority, actor-outcome selector, or state store. Folder placement is for control management, not semantic classification.
> Activation: the installed CI requires this file in full for a matching requested operation; file presence alone does not deploy it.
> Dependencies: Router entry as required by the CI; applicable reasoning controls through the Router. The CI owns operation/stage and Router-required entry; this procedure owns transformation, information-need declaration, and stopping.
> Failure behavior: obey CI/Router source, conflict, and block rules; unavailable pipeline blocks only its dependent transformation.
> Retained state: none outside the current task context.

## 1. Activation And Stop Contract

The pipeline operates within FTH; its operating scope does not set or expand the task target, or collapse project scope into any country, institution, module, or domain. AetherFire is a scoped target only when established by the request or routed controlling sources; it is not an alias for FTH. Preserve the requested target through seed extraction, decomposition, comparison, localization, and proposal composition. An AetherFire-targeted task stays within its relevant scope; an FTH/cross-domain task is not narrowed to AetherFire by default. Naming and file placement establish no semantic containment.

```text
FTH SCOPE != AETHERFIRE SCOPE
PIPELINE OPERATING SCOPE != TASK TARGET SCOPE
```

Activate for requested seed extraction, functional abstraction, implementation stripping, material primitive decomposition, FTH candidate comparison, application/localization within FTH, or an FTH implementation proposal.

Keyword occurrence alone does not activate this procedure. Ordinary fact lookup, audit, or canon externalization does not activate it unless the requested operation includes such a transformation.

Identify the requested operation and output stage before transforming input. If ambiguity changes the operation or stop point, use the CI's clarification or conditional-branch rules. The request, not the procedure's available stages, sets scope.

```text
REQUESTED OPERATION DETERMINES STOP POINT
```

| Requested operation | Stop at |
| --- | --- |
| Extract seed / recover functional core | Seed |
| Decompose material primitives | Primitives |
| Compare candidate with relevant FTH state | Comparison |
| Apply/localize candidate or propose implementation | Proposed local implementation |

Do not add simulation, second-order consequences, redesign, alternatives, or an integration plan unless the requested operation needs them. Application/localization produces a proposal, not a project-state mutation; acceptance remains governed by the CI.

## 2. Input Basis And Flow

Distinguish relevant current FTH state, new user input, and external information using the CI's truth-status rules. A user input may be a candidate, requirement, premise, or correction; do not flatten these roles into one status. Obtain current state through the Router whenever it is needed.

External information may help identify function, mechanism, constraint, relation, causal structure, or implementation-specific detail. It is analytical input, not local authority; do not import its implementation wholesale or assume its constraints govern the requested FTH target.

```text
REQUEST / INPUT
-> identify operation and stop point
-> establish relevant input basis
-> extract functional seed, when needed
-> decompose material primitives, when needed
-> cross-check relevant current FTH state, when needed
-> compose proposed local implementation, only when requested
-> STOP
```

This is not a rigid checklist. Use an already adequate seed or primitive set directly; derive preceding stages only when necessary for the requested transformation, not to fill a presentation template.

## 3. Seed Extraction

A seed is the functional or causal core that remains after non-essential implementation detail is removed. It is not a short summary. Preserve the input's intent and decisive relations; do not genericize until its meaning disappears. If the input already supplies that core, do not manufacture another abstraction.

```text
SEED != IMPLEMENTATION
```

When stripping implementation, retain details essential to the core's operation or intent. Do not reverse-define the original seed from a proposed implementation; mark a requested reinterpretation as a changed candidate.

## 4. Material Primitive Decomposition

Separate only components carrying functional or causal value for the requested operation. Examples include function, condition, actor/entity role, resource, authority, capability, constraint, interface, state, transition, dependency, pressure, information relation, input/output, causal relation, or failure path.

These are examples, not a required schema. A candidate need not contain every type; do not create a primitive to complete a slot. Preserve material relations between components without importing a universal architecture.

```text
DECOMPOSITION != GAP FILLING
```

Keep a necessary but unsupported relation unresolved. Use the CI's rules for explicit premises, conditional proposals, and unknowns; do not invent a link so decomposition looks complete.

## 5. Early Router Handoff

Before the first transformation that materially requires current FTH state, declare the information need and hand it to the active Router. This can occur before seed extraction, before decomposition, or during comparison/proposal composition; it is not a fixed step after primitives.

```text
information need
-> Router discovery / selection / required source loading
-> reconciliation / applicable controls
-> resume only the supported transformation
```

A self-sufficient candidate can be transformed without canon loading only where the CI permits it; this procedure cannot waive Router-required entry. Do not read canon merely because a diagram contains a Router step. If later work needs new current-state information, hand off again before using it.

The pipeline declares what information the transformation needs. The Router owns discovery, eligibility, controlling owners, source-authority routing, dependencies, closure, load modes, fallback, and source block/partial decisions. Do not scan all FTH merely because current-state information is required, invent source dependencies, choose authority, or substitute another source for a blocked premise. Continue only independently supported work when a dependent step is blocked.

## 6. Comparison And Proposal

For comparison, evaluate the seed/primitives against only the relevant routed current constraints. Report supported compatibility, conflicts, and unresolved dependencies; comparison alone does not request a repair or implementation.

When application/localization or implementation is requested, compose a bounded proposed implementation from the seed, material primitives, and relevant current constraints. Do not aim for the most complete system imaginable, silently change the seed to force compatibility, or repair current state to accommodate the candidate.

Missing decisive current information remains subject to the Router's block contract. An explicitly labeled design premise may support an independent conditional proposal under the CI, but cannot substitute for missing current facts or bypass their block. Neither compatibility nor a completed proposal grants acceptance.

## 7. Applicable Controls And Final Check

This procedure controls transformation and stopping; anti-drift controls protect reasoning in materially relevant domains. Use the Router's existing scoped selection and dependency rules, not a fixed stage-to-overlay mapping. Do not copy architectural, institutional, economic, actor-reception, or operational controls into this procedure.

Before output, check that the requested operation activated the procedure; input roles stayed distinct; abstraction preserved intent; decomposition added no unsupported components; any decisive current-state need passed the Router before use; applicable controls were obeyed; and output stops at the requested stage. Unavailable required controls block only dependent work under the existing CI/Router contract.
