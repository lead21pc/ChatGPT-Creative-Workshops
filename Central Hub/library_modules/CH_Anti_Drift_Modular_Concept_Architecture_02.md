# 3. Module Autonomy

A module may be an engine, concept, paracosm, faction, institution, actor group, rule set, simulation unit, interface, or bounded functional domain.

A module may independently be:

- autonomous;
- composable;
- portable;
- host-bound;
- state-sharing;
- actor-sharing;
- event-sharing;
- reusable;
- separately simulatable.

No property automatically implies another.

Repeated use with another module does not establish permanent coupling.

Temporary composition does not establish ownership, containment, authority, shared implementation, or shared ontology.

# 4. Typed Relation Graph

Represent architecture as a graph with explicit relation types.

Use the supplied concept's established typed-relation vocabulary where applicable. These subject relations are not Hub routing/dependency metadata. Descriptive relation classes may include:

```text

USES
GOVERNS

MAY_CONTAIN
MAY_RUN_WITH
MAY_RUN_WITHOUT
DERIVED_FROM

```

Do not collapse distinct edge types into parent/child.

Do not infer:

```text
A INTERACTS_WITH B -> A CONTAINS B
A OFTEN RUNS_WITH B -> A DEPENDS_ON B
A USES B -> A GOVERNS B
A PRECEDES B IN A DOCUMENT -> A IS ABOVE B
B IS DERIVED_FROM A -> A CURRENTLY OWNS OR CONTROLS B
```

If a relation type is UNKNOWN, keep it UNKNOWN or branch it. Do not select the most convenient edge.

# 5. Separate Graphs

Multiple graphs may describe the same entities without contradiction:

```text

SIMULATION REQUIREMENT GRAPH
OPERATIONAL USE GRAPH
CAUSAL GRAPH
AUTHORITY GRAPH
INFORMATION GRAPH
NARRATIVE PROVENANCE GRAPH

```

Example:

```text
Lore: Faction A BELONGS_TO World X
Simulation: Faction A MAY_RUN_WITHOUT Full World X
```

These claims can both be true.

Do not transfer an edge from one graph to another without an established bridge.

# 6. Composition Is An Operation

A runtime or fiction configuration may combine modules:

```text
Module A + Module B + Module C -> one configured run
```

This confirms only that the modules interact in that configuration.

It does not establish:

- permanent dependency;
- ownership;
- containment;
- shared authority;
- shared implementation;
- current genealogy;
- universal compatibility.

When the configuration ends, module relations return to their established state unless a valid transition changed them.

# 7. Shared Contract Is Not Shared Implementation

Two modules may expose the same interface or workflow while differing in payload, goal, rules, authority, constraints, and failure behavior.

```text
SHARED CONTRACT
!= SAME SUBSYSTEM
!= SAME ONTOLOGY
!= SAME IMPLEMENTATION
```

Shared terminology does not prove semantic identity.

When compatibility depends on a shared contract, check both sides of the interface. Do not validate only the caller or host.

# 10. Mechanism Does Not Select Outcome

When actors retain agency:

```text
mechanism changes conditions
-> actor receives available information, options, and constraints
-> actor chooses or fails to choose
-> other actors adapt
-> state changes or remains stable
```

Do not convert condition-setting into actor control, guaranteed trajectory, or predetermined outcome unless the source establishes that capability and authority.

```text
ENABLES != COMMANDS
PRESSURES != DETERMINES
POSSIBLE TRAJECTORY != CANON OUTCOME
```

# 11. Actor Information And Agency

An actor may act only from task-relevant information it can access, plus its established memory, belief, incentive, authority, capability, bias, and cognitive limits.

Do not grant:

- hidden canon;
- author intent;
- future knowledge;
- complete cosmology;
- engine definitions unavailable in-world;
- motives without evidence.

```text
SIMULATION KNOWS != ACTOR KNOWS
ACTOR KNOWS != ACTOR UNDERSTANDS
ACTOR UNDERSTANDS != ACTOR CAN ACT
```

Information access is a simulation variable, not narrative convenience.

## Function Allocation And Competence

For each task-material actor or institution, distinguish information access/observation, understanding, mandate, decision authority, execution capability, and outcome. "Handles the problem" establishes none of the remaining functions by itself; expertise does not grant command.

```text
OBSERVES != UNDERSTANDS
UNDERSTANDS != HAS MANDATE
HAS MANDATE != DECIDES
DECIDES != CAN EXECUTE
CAN EXECUTE != SUCCEEDS
```

These are non-implications, not required separate holders or a universal temporal pipeline. Mandate alone does not establish final decision rights; holding those rights does not prove a decision was made. Both co-location and separation require current-source evidence or an explicit labeled design premise.

Do not merge separate information, authority, decision, and execution functions merely to shorten the causal chain. Do not split a source-established unified actor merely to manufacture friction, delay, or narrative headroom. Preserve source-established restrictions on function overlap within their stated scope.

Shared institutional membership does not prove a shared information picture, interpretation, mandate, or executable resources. Trace only task-relevant established links and handoffs; missing decisive links remain UNKNOWN or require an explicit branch/block, not invented coordination, latency, powers, or success. This controls reasoning, not an organizational chart.

## Conditional Response Lifecycle

Apply only when the task materially depends on multiple conditional pathways, state-triggered availability, concurrent contingencies, response selection, or branch persistence/termination. Ordinary options, brainstorming, a branch name, or a trivial if/else do not require lifecycle analysis.

A contingency list is a response set, not a mandatory chronology or one preselected master plan. Keep only task-material distinctions:

```text
POSSIBLE BRANCH != AVAILABLE BRANCH != ACTIVE BRANCH
ACTIVE BRANCH != SELECTED RESPONSE != EXECUTED RESPONSE
EXECUTED RESPONSE != SUCCESSFUL RESPONSE != CANON EVENT
BRANCH OPENS != BRANCH MUST BE TAKEN
```

Here, availability means the relevant gates are met now; active means a contingency is currently operative, not merely eligible. Selection records a choice; execution records the actual attempt, not its success. These are non-implications, not mutually exclusive states, mandatory stages, or an in-world taxonomy. Canon status remains a separate truth-status question under Hub CI and the task-declared source/admission process.

Evaluate availability from the current state and only material information, authority, capability, constraints, and timing. Use sections 11-12 rather than assuming that knowledge grants authority, capability, or a choice. A world-true trigger alone cannot activate an actor-mediated response:

```text
WORLD STATE != ACTOR OBSERVED STATE != ACTOR INTERPRETED STATE
TRIGGER EXISTS != TRIGGER OBSERVED != TRIGGER UNDERSTOOD
```

Use a supported actor-specific information path and relevant established appraisal when receipt or interpretation matters. Preserve source-established automatic mechanisms within their trigger, access, and operating limits; do not require conscious receipt or fresh selection for every transition, invent a universal sensor, or assume an available response fires automatically.

Several contingencies may run concurrently; activating one does not terminate the others. Keep availability, current activity, and response selection distinct for each material branch. Do not force XOR, assume compatibility, or invent competing actors: check only supported resource, timing, authority, or interface constraints that can change coexistence.

When duration matters, retain the supported activation, persistence, and termination/transition conditions. Re-evaluate affected branches after a material state, objective, information, or feasibility change, or an established termination condition being met. Close, pause, or transition a branch when its required basis no longer holds; do not retain it indefinitely because it once opened. A threshold may open a transition candidate without selecting it. Do not close another branch unless its own conditions are affected.

Selection does not establish execution; an attempt does not establish success. Preserve supported selection and attempt history after failure, cancellation, or loss of availability. A tactical failure does not prove every strategic objective failed; surviving evidence or another valid objective may support another available response, not automatic selection or success.

Section 16 still forbids choosing an ending and inventing its trigger/evidence. Story pressure or thematic usefulness alone cannot activate or choose a response; preserve only source-established causal effects within their exact limits. Preserve each input's and result's truth status, including UNKNOWN, PROPOSAL, and DEFERRED. A successful simulated branch remains outside canon pending the normal explicit scoped acceptance process.

This subsection owns branch distinctions only. Hub Router retains package composition/read validation; the concept core/catalog retain local selection; paired WIL contributes institutional coherence within its own gates. Preserve material signal receipt/appraisal, operational feasibility/execution, capture/rescue/lethal-resolution and other domain-specific interface/stopping boundaries. FTH-only controls are not imported or dependencies here. Return needs beyond this pair to the existing Hub owner; do not invent a replacement control, assume unavailable expertise or authorize a pipeline. Keep unsupported decisive links UNKNOWN/blocked and continue sufficient independent work.

No complete lifecycle, branch registry, actor matrix, scoring system, scenario database, or workflow engine is required. Stop at section 19's task-local closure.
