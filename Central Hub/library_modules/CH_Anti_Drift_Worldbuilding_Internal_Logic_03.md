# 1. Core Purpose

Build or audit internally coherent world structures without treating Earth realism as the default attractor.

Ask:

```text
Can this structure operate under the world's established ontology,
constraints, interfaces, and consequences?
```

Do not ask first:

```text
Would Earth history usually produce this structure?
```

Internal logic requires traceable function, authority, information, resources, constraints, failure, and consequences. It does not require historical familiarity.

```text
COHERENCE > REALISM
UNFAMILIAR != INCOHERENT
PLAUSIBLE != ESTABLISHED
UNKNOWN != PERMISSION TO INVENT
```

# 2. Activation And Routing

Use this overlay when the user asks to:

- design or expand a world subsystem;
- audit systemic coherence;
- test an institution or social order;
- propagate a major established or hypothetical change;
- examine feedback, succession, adaptation, or long-term viability;
- compare multiple labeled design branches.

Do not activate the full overlay for a local question that already has sufficient interface closure.

For economy, funding, labor, housing, trade, logistics, market shock, or state-stabilization tasks, preserve the specialized boundary: this experiment imports no FTH Economy control. Return a material need beyond this overlay to the existing Hub owner without activating another package/pipeline or inventing an Economy clone. Respect any task-supplied economic depth, MUST_OPEN/MAY_STOP, UNKNOWN and output constraints; absent decisive domain support remains UNKNOWN/blocked, not permission for a complete economic simulation.

World logic contributes ontology checks, institution-design primitives, social/political structure, feedback, temporal logic and bounded cross-domain propagation. It does not take ownership of economic depth or state stabilization, and must not override the active task boundary.

```text
DESIGN POSSIBILITY != REQUIREMENT TO OPEN THE DESIGN
SYSTEMIC RELEVANCE != CURRENT TASK RELEVANCE
```

# 3. Active Design Boundary

Derive an `ACTIVE DESIGN BOUNDARY` from the user request.

The boundary may be limited by:

- subsystem;
- institution;
- actor class;
- polity;
- geography;
- time horizon;
- causal transition;
- proposal branch.

Nodes outside the boundary remain part of the world. Keep them as established context, external pressure, UNKNOWN, or deferred edge as appropriate.

Open an outside node only when:

1. the user requests it;
2. an interface crossing changes the current conclusion;
3. a contradiction cannot be evaluated without it; or
4. the current change directly alters that node's state.

Do not expand the boundary merely because broader propagation is imaginable.

# 4. Ontology And Invariants

Ontology defines which kinds of entities, capacities, relations, and processes can exist.

For each task-relevant ontological element, establish or label:

- what kind of entity or process it is;
- what it can affect;
- access conditions;
- limits and costs;
- invalidation or resistance conditions;
- relevant interfaces.

Invariants are boundary rules, not decorative lore.

Do not add an invariant only to force a preferred outcome. Do not silently revise an established invariant to preserve a proposal.

If a proposal conflicts with an invariant:

```text
REJECT THE PROPOSAL
or
LABEL AN EXPLICIT ALTERNATE SYSTEM VERSION
```

An alternate version is not current canon.

# 5. Actors, Information, And Resources

Do not treat broad labels such as state, people, nobility, religion, market, or military as unitary actors when internal differences change the result.

For each active actor, use only the task-relevant parts of:

```text
GOAL
INFORMATION
BELIEF
AUTHORITY
ACCESS
CAPABILITY
RESOURCE
INCENTIVE
CONSTRAINT
RISK
AVAILABLE ACTION
```

Actors may be mistaken, irrational, short-sighted, ritual-bound, or self-destructive. Their behavior must still be traceable to their information, beliefs, incentives, constraints, or accepted psychology.

Resources may include material, energy, labor, time, information, legitimacy, reputation, magical capacity, identity, access, attention, memory, lifespan, or other ontology-specific values.

When a resource changes a transition, identify:

- source;
- controller;
- access path;
- renewal or depletion;
- bottleneck;
- transfer loss or delay;
- scarcity consequence.

Do not require a complete resource ledger when the interface is sufficient.

# 6. Institution Design

Create an institution only when a function requires an organized carrier.

Minimum design interface:

```text
FUNCTION
INPUT
OUTPUT
ACTOR / AUTHORITY
INFORMATION PATH
RESOURCE SOURCE
ACCESS
ENFORCEMENT OR IMPLEMENTATION
CONSTRAINT
DEPENDENCY
FAILURE
SUCCESSION OR REPRODUCTION, if time matters
```

Do not add an institution because a familiar society normally has one.

Start from function, then select an ontology-compatible form:

```text
function
-> required authority and resource
-> valid carrier
-> interface
-> constraint and failure
```

The carrier may be a ministry, guild, lineage, cult, algorithm, ritual network, sentient place, distributed protocol, or another source-compatible structure.

This list offers design classes, not canon candidates.

---

# 7. Enforcement And Decision Structure

Separate:

```text
RULE MAKING
INTERPRETATION
IMPLEMENTATION
RESOURCE ALLOCATION
VETO / REFUSAL
```

Power in one category does not prove power in another.

A binding rule needs a task-relevant path such as:

```text
rule
-> detection or recognition
-> interpretation / judgment
-> implementation
-> consequence
```

If the path is incomplete, classify the rule as symbolic, customary, aspirational, contested, or UNKNOWN rather than assuming enforcement.

Legitimacy explains why actors accept or tolerate an authority. It may derive from source-established lineage, religion, performance, contract, ownership, protection, history, ontology, or another mechanism.

Legitimacy does not prove morality, consensus, or unlimited capacity.

---

# 8. Social Reproduction And Stratification

When long-term viability is in scope, determine how the relevant system reproduces:

- actors;
- knowledge;
- authority;
- membership;
- property or access;
- skills;
- norms;
- succession.

A hierarchy persists only through a mechanism such as enforcement, dependency, belief, access control, technical asymmetry, ontology, coordination cost, or accepted exchange.

Do not assume Earth-standard family, class, education, employment, property, or inheritance models.

Open social reproduction only when duration, succession, legitimacy, resistance, or institutional continuity changes the current task.

---

# 9. Cross-System Interfaces

Subsystems need not share one internal logic. They need a coherent interface where they interact.

For each active crossing, ask:

```text
WHAT CROSSES?
WHO CONTROLS IT?
WHO MAY REFUSE?
WHAT INFORMATION TRAVELS?
WHAT DELAY OR LOSS EXISTS?
WHICH RULE OR JURISDICTION APPLIES?
WHAT HAPPENS WHEN THE INTERFACE FAILS?
```

Do not infer containment from interaction.

```text
INTERACTS_WITH != BELONGS_TO
USES != CONTROLS
DEPENDS_ON != OBEYS
CAN_ACCESS != HAS_AUTHORITY
```

If two subsystems use different ontology or value systems, establish only the equivalence, translation, custody, or exchange mechanism required by the active task.

---

# 10. Anti-Realism Discipline

Real-world structures may be used as:

- labeled comparison;
- negative test;
- mechanism analogy;
- requested reference;
- feasibility check for a real-world premise.

They must not become default world structure.

Do not automatically add:

- modern state bureaucracy;
- fiat money or banking;
- corporations;
- Earth-standard professions;
- familiar class systems;
- industrialization pathways;
- GDP, population, or technology as universal power scores.

When several mechanisms satisfy the same function, prefer the one best supported by current ontology, invariants, sources, and interfaces. Do not prefer familiarity by itself.

Absence of design may remain UNKNOWN. A familiar Earth analogue is not a valid gap filler.

---

# 11. Extraordinary Capability Is Still A Subsystem

Magic, technology, divine action, or exceptional personal power does not erase interfaces.

When an extraordinary capability changes a function, trace only the affected dependencies:

```text
capability
-> removed dependency
-> new bottleneck or access condition
-> displaced controller
-> changed actor options
-> bounded consequence
```

Do not propagate a generic Earth checklist.

If a capability is unlimited, free, instant, riskless, and universally accessible, treat that combination as a major premise requiring explicit authorization. Do not preserve it as a convenient local exception.

```text
EXCEPTIONAL CAPABILITY != INFINITE INSTITUTIONAL CAPACITY
MAGIC != AUTOMATIC SOLUTION
```

---

# 12. Bounded Causal Propagation

For a major established change or labeled hypothetical, use the shortest sufficient chain:

```text
TRIGGER
-> actor receives or misses information
-> actor updates available choices
-> institution acts, refuses, or fails
-> relevant resource / authority / access flow changes
-> affected interface changes
-> new bounded state
```

Propagate only along edges that:

- change the active conclusion;
- produce a contradiction;
- alter an active actor's options;
- create a real crossing of the design boundary; or
- were explicitly requested by the user.

For plausible but inactive consequences:

```text
MARK DEFERRED
DO NOT SIMULATE
DO NOT CANONIZE
```

```text
LOCAL CAUSAL CLOSURE != GLOBAL WORLD COMPLETENESS
PROPAGATION != PERMISSION FOR DOMAIN EXPANSION
```

---

# 13. Feedback And Temporal Logic

Open feedback only when it changes stability, adaptation, concentration, decline, or failure.

Positive feedback requires a limiting condition such as saturation, counterforce, resource ceiling, delay, or external shock unless runaway change is the explicit branch.

Negative feedback may explain why a system remains inside a stable range without reaching an ideal equilibrium.

Separate:

```text
FORMATION CONDITION
MATURE MECHANISM
CURRENT STATE
DEGRADATION PATH
SUCCESSION / REPLACEMENT PATH
```

A structure may survive after its original function disappears only through a new function, inertia mechanism, dependency, or coercive path supported by source or a labeled proposal.

Do not make long-term effects immediate.

---

# 14. Failure And Stress Testing

Every designed system needs the failure information required by the task.

For a bounded task, one decisive failure mode may be enough.

Use all three classes only when the user requests full design, resilience analysis, or a system audit:

```text
NORMAL FAILURE
ADVERSARIAL / EXPLOITED FAILURE
STRUCTURAL FAILURE AFTER BASELINE CHANGE
```

Stress tests may vary resource, leadership, information, legitimacy, access, monopoly, population, conflict, or an ontology-specific constraint.

Do not invent a shock merely to make the setting dramatic.

A valid stress result may be:

```text
ADAPTATION
CONTROLLED DEGRADATION
FRAGMENTATION
COLLAPSE
BLOCKED / UNKNOWN
```

Outcome follows from the branch state, not genre pressure.

## Imperfection And Design Intent

An ambiguity, loophole, vulnerability, inefficiency, leak, or attack surface is not by itself a coherence defect or a repair mandate. When material, distinguish the supported roles; they may overlap, and no complete classification is required:

```text
UNINTENDED FAILURE
CONTROLLED LOOPHOLE
TOLERATED COST
DELIBERATE EXPOSURE
INCENTIVE MECHANISM
SURVEILLANCE / EXTRACTION SURFACE
INSTITUTIONAL TRADE-OFF
UNKNOWN INTENT
```

Establish intent from controlling sources or explicit scoped author decisions, not from a plausible benefit. Authorial design intent does not establish in-world actor knowledge, control, or tolerance. Preserve UNKNOWN intent, limits, and accepted spillover rather than inventing a designer, permission, or containment mechanism.

For a confirmed intentional imperfection, trace only task-needed, supported aspects:

```text
FUNCTION
WHO BENEFITS / WHO BEARS COST
BOUNDARY / ACCEPTED SPILLOVER
FAILURE WHEN IT ESCAPES THAT BOUNDARY
```

Do not automatically close, clarify away, or redesign that imperfection because a cleaner, safer, fairer, or more efficient system is imaginable. If changes are requested, label proposals and identify the established function or trade-off they preserve or sacrifice. Analysis may expose harm, genuine contradictions, unintended failure, or loss of control; intent does not guarantee containment or success.

```text
KNOWN VULNERABILITY != DESIGN FAILURE
CONTROLLED LOOPHOLE != BROKEN SYSTEM
INTENTIONAL AMBIGUITY != MISSING DEFINITION
EXPLOITABLE INTERFACE != INTERFACE THAT SHOULD BE CLOSED
PLAUSIBLE FUNCTION != CONFIRMED DESIGN INTENT
CONTROLLED VULNERABILITY != UNLIMITED VULNERABILITY
INTENTIONAL AMBIGUITY != PERMISSION TO INVENT ITS SCOPE
KNOWN EXPLOIT != PROOF THAT EVERY EXPLOIT IS TOLERATED
```

# 15. Causal-Load Industries And Professions

Industry or profession design is optional and scope-gated.

Open it only when:

- the user asks for industry, profession, production, or strategic-economy design;
- a changed node directly controls a relevant bottleneck;
- a profession carries authority, information, reproduction, access, or resource flow that changes the current conclusion; or
- polity-level balance is explicitly in scope.

Do not create an industry catalog for completeness.

When the user requests alternatives, produce at least two functionally distinct labeled proposals. Do not create two names for the same function.

A strategic or flagship industry is required only when strategic economic competition is in scope. It must be supported by a real leverage path such as monopoly, dependency reduction, validation authority, mobilization, reproduction, access, or ontology translation.

Do not assign one flagship industry to every polity by default.

The active task boundary and any supplied specialized economic constraints control how deeply economic mechanics may be opened; missing decisive support returns to Hub, not a fabricated Economy control.

# 16. Contradiction Checks

Check only task-relevant contradiction classes:

## Rule

Two active rules cannot both hold under the same conditions.

## Resource

The system consumes or promises more than the established source, capacity, or renewal path can provide.

## Authority

Multiple actors claim decisive authority without an established hierarchy, arbitration, partition, or conflict state.

## Information

An actor acts on knowledge without a valid path, timing, or access condition.

## Incentive

The system requires persistent costly behavior without sufficient coercion, belief, compensation, mistaken information, long-term benefit, or ontology-specific constraint.

Contradiction does not authorize invention. Report, branch, or block it according to current truth status.

# 17. Design Workflow

Use only the steps required by the request:

1. Define the active boundary and truth status.
2. Identify the relevant divergence from familiar reality.
3. Load established ontology and invariants.
4. Identify active actors, information, resources, and authority.
5. Trace required flows and interfaces.
6. Create or audit institutions by function.
7. Add task-relevant failure and feedback.
8. Propagate consequences to the boundary.
9. Mark blocked, conditional, deferred, and unresolved edges.
10. Return proposals without mutating canon.

Do not require every step for a narrow task.

# 19. Stop Rule

Stop when the active design question has enough causal closure to support a valid conclusion, branch, rejection, or blocked result.

Do not continue merely to complete:

- every subsystem;
- every actor;
- every profession;
- every polity;
- every feedback loop;
- every possible consequence;
- a full history;
- a complete economic model.

If an unopened layer cannot change the current answer, keep it closed.

If a deferred consequence may matter later but does not cross the active boundary now, label it briefly and stop.
