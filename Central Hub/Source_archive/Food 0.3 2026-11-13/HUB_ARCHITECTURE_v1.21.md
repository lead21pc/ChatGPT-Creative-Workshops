# Central Hub shared architecture

Module ID: HUB-CORE-ARCH
Runtime role: CORE_ARCHITECTURE
Scope: shared topology, ownership, technical composition and contextual data interfaces
Status: ACTIVE
Version: 1.21

## Ownership

Hub CI governs turn function, operation, stage, truth/state, action authority, verification need and explanation. Hub Router selects and composes scoped package contributions and owns generic dependency, read and failure rules. Root and local Catalogs declare admission, identity and bindings. A package selects its own leaves and owns domain semantics and local execution state. A pipeline owns its internal procedure. The platform performs actual retrieval and tool calls.

Runtime controls use English. User content, quotes and human documentation follow their own language requirements. The controls are behavioral instructions. Selection is neither retrieval nor execution.

## Installed surfaces and identity

- Project Instructions: HUB_CI_v1.3.md.
- Project Sources: HUB_ROUTER_v1.2.yaml, this Architecture, HUB_PACKAGE_CATALOG_v1.21.yaml and the exact AIS Project Source declared by the root Catalog. Install CONTEXT_SNAPSHOT.md and HUB-USER-PROFILE-CONTRACT_v1.0.yaml as Project Sources and consult them only on the corresponding scoped need.
- ChatGPT Library: Central Hub Config is the sole discovery root for Library bindings. A package has one direct folder containing its active artifacts. The root has Technical, Concept Development, Authoring, ImageT, Shopping and Food package folders and a shallow Shared folder for shared data objects. Folder membership expresses package ownership only. No nested functional taxonomy.
- Installation records, static integrity inventories, tests, templates and archives are repository material.

One package has one accepted runtime binding. Apply Hub Router's exact binding and FULL_FILE checks. A Library artifact has one stable Module ID, one Package ID (shared core infrastructure can omit it), runtime role, scope, status and bound version. Markdown headers and equivalent YAML keys carry the same meanings. Filenames/folders do not confer identity, role, dependency, authority or activation. Library revision and artifact version are independent.

Canonical Library IDs use HUB-<PACKAGE>-<ARTIFACT> or HUB-<PACKAGE>-<SUBDOMAIN>-<ARTIFACT>. Package tokens are TECH, CON, AUTH, IMAGET, SHOP and FOOD. AIS is reserved for AIS. Subdomain is a functional label only. Root inventory owns accepted entrypoints and local interfaces, not leaves or procedures. Install filenames use <Module-ID>_v<Version>.<extension>. Use approved bindings; no aliases or dual active identities.

## Package interfaces

A singleton delegates directly to its entrypoint. A growing package uses the local selection interface it declares, with Catalogs for independently selected inventory where needed. Local inline selection can be sufficient for one optional procedure. Resolve only selected leaves and hard dependencies. Root admission and package execution remain distinct. No selected package grants permission to start another.

Shared roles include CORE_ARCHITECTURE, CORE_ROUTER, PACKAGE_CATALOG, DOMAIN_CONTROL, REASONING_PROFILE, CAPABILITY, DOMAIN_PROCEDURE, PREFERENCE and TOOL_PIPELINE. Roles describe responsibility, not priority. REFINES narrows only its matched scope. COMPLEMENTS joins independently applicable contributions. REQUIRES is an explicit hard dependency. Router owns closure, conflict validation and dependent failure.

## Continuity and scope

Keep the same conversation and reuse accessible, task-relevant outputs as scoped inputs. Preserve source role, qualifiers, evidence, current/provisional/rejected/open status and limits on changing them. Composition or output never grants authority or acceptance. Explicit task data flow creates no persistent mode or hard module edge. Keep locks, approval, provenance checks and domain-specific state with the owning module. Re-evaluate scope and refresh affected reads when their evidence no longer suffices.

## Shared data by need

For explicit Context Snapshot creation, exact reference or semantic comparison, use the bound Project Source CONTEXT_SNAPSHOT.md. A Snapshot is data with a fixed payload for its ID, separate from Library module resolution. Missing payload or contract blocks only dependent Snapshot work.

For HUB-USER-PROFILE, require selected consumer, exact object, purpose and material need before any retrieval. Validate against the full bound HUB-USER-PROFILE-CONTRACT_v1.0.yaml. It owns the allowlist, schema, read-only user ownership, need-before-read and exact private object contract. The four objects are independently read only if admitted, under Central Hub Config/Shared. Profiles are data; prefer explicit current input for the current task. Missing or denied data blocks only dependent personalization. Consumer modules retain domain interpretation. Context Snapshot has no dependency on Profile.
